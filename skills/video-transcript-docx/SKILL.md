# 视频/音频 → 中文文字稿 docx

全本地流水线，不上传用户数据、不碰账号：

```
视频链接 ──yt-dlp──> 音频 ──ffmpeg──> 16k 单声道 wav ──FunASR──> 原始文字

原始文字 ──> 定向纠错 ──> 按话题分段 ──> docx（深浅两版）──> 自检 ──> 交付 ──> 回写经验（回到本文件）
```

> **本技能自带回写机制。** 每次交付完，把这一趟的教训写回本文件——**不回写，下次还会
> 踩同一个坑**。具体怎么写见文末「**把这次的教训写回本技能**」，那一步和交付一样是必做的。
> （同款机制在 `courseware-to-docx` 里已经跑起来了。）

## 先做一件事：探字幕

**别急着下载音频。** 先看这个视频有没有现成字幕——有的话直接取，比跑 ASR 又快又准
（人工字幕的专有名词通常是对的）。

```
uv run --with imageio-ffmpeg python "<技能目录>\scripts\prepare_audio.py" "<url>" "<工作目录>" --probe
```

- 报 **usable subtitles** → 用 yt-dlp 的字幕下载（`--write-subs --sub-langs zh.*,en.*`），
  跳过 ASR。字幕是 SRT/VTT，转文字很省事。
- 报 **no usable subtitles** → 走 ASR。

**注意**：只列出 `danmaku` 等于**没有字幕**。弹幕是飘过去的观众评论，不是讲稿。B站的
AI 字幕需要登录 Cookie 才可见，探不到属正常——**不要为了拿 AI 字幕去读用户的浏览器
Cookie**，那等于拿用户登录态，除非用户明确同意。

## 取音频

```
uv run --with imageio-ffmpeg python "<技能目录>\scripts\prepare_audio.py" "<url-or-本地文件>" "<工作目录>"
```

产出 `<工作目录>\audio16k.wav`。本机没有系统 ffmpeg（装它要管理员权限），脚本从
`imageio-ffmpeg` 包里借一个静态二进制用，约 87 MB，用完就搁着，不用装任何东西。

## 转写

```
uv run --no-project --python 3.10 --with funasr --with modelscope --with "transformers>=4.40,<5" --with "numpy<2" --with torch --with torchaudio python "<技能目录>\scripts\run_asr.py" "<工作目录>\audio16k.wav" "<工作目录>\transcript.txt" "<工作目录>\sentences.json" --hotwords "<空格分隔的热词>"
```

**这条命令行不要改参数**，`--python 3.10` / `transformers>=4.40,<5` / `numpy<2` /
`torch` 缺一个就跑不起来，原因见 `references/pitfalls.md`。首次跑要下约 1 GB 模型，
之后有缓存。

**先设镜像**，否则大包会假死（境外源实测卡 4 分钟无输出，换清华源 7 秒装完）：

```powershell
$env:UV_DEFAULT_INDEX = "https://pypi.tuna.tsinghua.edu.cn/simple"
```

**热词**：长任务后台跑（`run_in_background`）。它的效果**有限**——只能修模型词表里本来
就有的词（`markdown`、`红黑树` 能修）。`Obsidian`、`Kruskal` 这类外来专名带不动，
而且热词还可能被误插到不相干的位置。热词值得给，但别指望它，**纠错那一步该做还是要做**。

## 纠错（关键步骤，不能省）

拿到 `transcript.txt` 后：

1. **通读全文**，挑出专有名词错误（工具名、书名人名、术语是重灾区）。
2. 抓上下文，判断本来应该是什么。
3. 写成 `rules.json`：`{"replacements": [["正则", "替换"], ...]}`。
4. 生成 docx，**看它报的每条规则命中次数**——命中 0 次的规则要么多余、要么写错了。

写规则的技术要点（**中文旁边不能用 `\b`**、错法会跨版本变化、一个词可能有多种含义、
顺序敏感）全部在 **`references/corrections.md`**，动手前先读它。

**哪些别碰**：口语的停顿、重复、口头禅是原话，删掉是篡改——所以忠实版和精简版各出一份，
让用户自己挑。**判断不出原话的地方就留着**，交付时明确列出来，绝不猜。

## 生成 docx

```
uv run --no-project --python 3.10 python "<技能目录>\scripts\make_docx.py" --input "<工作目录>\transcript.txt" --outdir "<工作目录>\out" --title "<视频标题>" --name "<文件名前缀>" --rules "<工作目录>\rules.json"
```

默认产出四份：`忠实/精简` × `深色/浅色`。

**为什么手写 OOXML 而不用 python-docx**：本机应用程序控制策略拦截了 `lxml` 的原生
DLL，`python-docx` 直接不可用。docx 本质是个 ZIP 装几个 XML，用标准库写反而更灵活。

**深色版必须给的原因**：Word 默认不打印页面背景色；部分手机阅读器不显示段落底纹，
会出现白底白字。**所以浅色版不是备选，是必需品**，两份都给。

## 自检（交付前必做）

```
uv run --no-project --python 3.10 python "<技能目录>\scripts\verify_docx.py" "<工作目录>\out" --stale "AR,IR,OBC,crystal" --expect "Obsidian,AI,Kruskal"
```

手工拼的 XML 很容易出细微错误，**打不开的 docx 比没有文件更糟**。它会检查 ZIP 部件
是否齐全、每个 XML 是否能解析、深色背景开关是否配对，以及残留的错误串数量。

若想再确认一次能不能真读出来，用 `mcp__cherry-tools__to_markdown` 读其中一份——
能读出内容就说明解释器认它。

## 交付

- **优先给本地路径**：把文件放到用户能找到的目录（源视频/音频同目录），在回复里列清
  文件名。**默认不走 IM 投递**——用户 2026-10-06 已明确叫停把 docx 发到微信/手机
  （手机打开乱码；当时是在 `courseware-to-docx` 的输出上实测的，**本技能出的是同类
  手写 OOXML docx，按同一规则处理**）。要发 IM 先问一句。
- 若确实要发 IM：`mcp__cherry-tools__notify` 的 **file_path 必须在会话工作区内**
  （先复制进去再发，否则报 `Path is outside the workspace`）。每个文件一次 notify，
  且**先发一条试水**——实测连续投递时第 2 条起会报 `prepare failed`，
  连纯文本都发不出去。
- 交付说明里必须讲清楚：
  - **这是机器转写，未逐句人工校对**
  - 修了哪些（给清单，让用户能复核）
  - **哪些判断不出、原样留着**
  - 深色版的已知局限

## 把这次的教训写回本技能（**每次都要做**）

**这个技能是靠一次次实测长出来的，不是一次写完的。** 每交付完一批，花几分钟回写一遍。
不回写，下次同样的坑照踩。

### 先过一遍这几问

| 这一问 | 命中后写到哪里 |
|---|---|
| 有脚本报错？或者**没报错、但根本没跑**（解释器不对、参数被改）？ | 那个脚本所在的步骤 |
| 探字幕**判错了**（把 `danmaku` 当成字幕、漏掉了能用的字幕）？ | 「先做一件事：探字幕」 |
| 某个依赖组合变了（`transformers` / `numpy` / `torch` 版本、模型下载失败）？ | 「转写」+ `references/pitfalls.md` |
| 热词**修好了没**？有没有被误插到不相干的位置？ | 「转写」的热词一段 |
| 纠错规则**命中 0 次**？某个错法跨版本变了？ | 「纠错」+ `references/corrections.md` |
| 用户提了新要求，或**明确叫停了某个做法**？ | 对应步骤。叫停的写成"**不要……**"，语气明确 |
| 哪一步明显慢？（首次下模型、批量的总时长） | 那一步，**附对策**，别只记现象 |
| 我自己犯了什么错？ | 那一步，写成**自查规则** |
| 用户的做法和我原先设想的不一样？ | 对应步骤，**以用户的做法为准** |

### 写到哪（这条最容易做错）

- **每次都要遵守的操作规则 / 判据** → 直接写进 SKILL.md **对应的那一步里**，就近放。
  别一律堆到文末——堆到文末的规则，下次跑的时候没人会翻到。
- **细节、长例子、一次性的排查过程** → 写进 `references/*.md`（这个技能已有
  `corrections.md` 和 `pitfalls.md` 两个筐），SKILL.md 里只留一句指路。
- **环境事实**（解释器路径、网络限制、应用控制策略这类**换台机器就变**的东西）→
  写进跨会话的 FACT.md / 项目记忆，**不要**污染 skill。
- **和这条流水线无关的约定** → 也不要写进来。skill 是要能带到别的机器上用的。

### 三条纪律

1. **SKILL.md 是操作手册，不是日志。** 写"遇到 X 就做 Y"，不写"某年某月某日我遇到 X"。
   日期只在判断新旧确实需要时保留。
2. **同一件事别记两遍**；发现重复就合并。更要紧的是：**发现旧条目和这次实测不符，
   直接改掉**——skill 里的经验也会过期，过期的经验比没有更坏。
3. **写完把 frontmatter 的 `version` 递增一位**（有实质修改就 +0.1）。这样一眼看得出
   交到用户手上的是哪一版经验。

### 一句话版

**交付 → 回写 → 升版本号。** 三步连在一起，做完才算收工。

## 批量处理

用户常要一次处理一批课程视频。遍历目录、逐个跑，但注意：

- **跳过已经处理过的**（输出 docx 已存在就跳），否则重跑一遍要等很久
- **失败的单独记下来**，别让一个视频挂掉就中断整批
- 每个视频的纠错规则是**独立的**——不要拿上一个视频的工具名去套下一个
- 批量跑之前先拿**一个**跑通并让用户确认质量，再铺开

## 脚本

- `scripts/prepare_audio.py` —— 探字幕 / 下载音频 / 转 16k 单声道 wav。依赖 `imageio-ffmpeg`。
- `scripts/run_asr.py` —— FunASR 转写（SeACo-Paraformer + VAD + 标点），输出文本和逐句时间戳。
- `scripts/make_docx.py` —— 纠错 + 分段 + 生成四份 docx。**纯标准库，无外部依赖。**
- `scripts/verify_docx.py` —— 交付前自检。**纯标准库。**

## 参考

- `references/corrections.md` —— 怎么找 ASR 错误、怎么写规则、哪些该改哪些别碰。**动手纠错前必读。**
- `references/pitfalls.md` —— 依赖、镜像、系统策略、热词的实际坑。遇到报错先查这个。
