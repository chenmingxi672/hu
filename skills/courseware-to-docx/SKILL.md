# 课件 PDF → 定稿 docx

```
课件 PDF ──渲染成图──> 逐页读 ──> 整理成 md ──> 补全略去的证明 ──> 拆原文版/补充版

pandoc ──> docx（原生公式）──> 深浅两版 ──> 自检 ──> 交付 ──> 回写经验（见「第八步」）
```

> **本技能自带回写机制。** 每次交付完，把这一趟的教训写回本文件——**不回写，下次还会
> 踩同一个坑**。具体怎么写见文末 **第八步**，那一步和交付一样是必做的。

## 第一步：先判断 PDF 能不能直接读文字

**别急着逐页看图**，先探一下。文字层能用的 PDF 直接提取，快得多。

```
uv run --with pymupdf python "<技能目录>\scripts\probe_pdf.py" "<pdf 路径>" "<输出目录>" --probe-only
```

- **文字层可用** → 复制进会话工作区，用 `mcp__cherry-tools__to_markdown` 转出 markdown 再读。
- **文字层不可靠** → 渲染成图逐页看。

**乱码的判据**：正常中文课件应该通篇通顺；如果满屏是 `ThHCTab`、`ITEAC`、`C= EPJ`
这类**拉丁字母垃圾**，那是**字体缺少 Unicode 映射**——不是扫描件，但同样读不出文字。

> **这一步的完整做法见 `pdf-to-notes` 技能**（探测、渲染参数、分批读图的技巧都在那里）。
> 本技能和它是衔接关系：`pdf-to-notes` 负责"读出来"，本技能负责"做成定稿"。
> 读图的活儿别在这里重造。

### 页数多的时候：边读边落盘，别只记在上下文里

**这是本技能最耗时的一步**，也是唯一可能跑上几十分钟的一步。实测一份 60 页的课件
（文字层碎成每行一字，只能渲染成图逐页看）是整次任务耗时的大头——**读图慢，
后面的转 docx / 上色 / 自检全加起来也就几秒。**

由此有两条经验：

1. **读完一批就把转录结果写进 md，不要攒在上下文里等最后一起写。** 会话上下文一旦
   被压缩，之前读过的图就不在上下文里了（只剩一段摘要），**为写出忠实的稿子只能重读一遍**。
   实测为此白读了 24 页。边读边落盘，压缩了也不怕。
2. **页数多时可以考虑分派子代理并行转录**（各负责一段页码，各自写一个 md 片段），
   最后合并。转录质量要抽查——数学公式的细节容易走样。

批次的划分、渲染参数（`--dpi`）这些，仍按 `pdf-to-notes` 技能的做法。

## 第二步：整理成 markdown

按**内容本身的脉络**组织，不要按页码流水账：开头一段把主线串出来，按主题分节，
定义/定理/例题/证明各归各位，**证明写全**，数学公式写成 LaTeX（行内 `$...$`，独占一行 `$$...$$`）。

来源、页码、教材出处这些信息在开头用引用块交代清楚，方便日后回查。

## 第三步：补全被略去的证明（**本技能的核心**）

**这一步不能省。** 课件里讲师常用一句话把整个证明带过去——对他当堂的学生够了，
但对着一份整理稿的读者，那就是死路。

```
python "<技能目录>\scripts\find_gaps.py" notes.md
```

它列出所有可疑处（"由另页例可知""同理可证""显然"…）及上下文，**外加一道完整性检查**
（哪些定理/例题根本没给证明）。**它不判断**，逐条回原文看，标准只有一条：

> **只靠这份稿子，读者能不能自己把这一步补出来？**

**两个实测教训（2026-10-06）**：

- **先确认它真的跑了。** 本机 PATH 上的 `python` 是 Microsoft Store 的占位 stub，
  会打印 "Python was not found" 然后什么都不干。别把它和别的脚本塞进同一条命令：
  那次 `find_gaps.py` 和 `split_supp.py` 一起跑，我看到了 split 的输出就往下走了，
  **没回头发现 find_gaps 一个字都没扫**——等于这一步整个空过去了。**每个脚本单独看它的输出。**
- **对重组过的稿子，完整性检查会大批误报。** 它的判据是"标题后面跟没跟证明"，
  所以例题、定义、推论都会被判成"没有证明"，实测一份 60 页的稿子报了 20 条。
  但**别因为噪音多就跳过它**——那 20 条里藏着 3 处真缺口（"$\mathbb{R}^{*}$ 是交换群"
  "$\{X=(x_{1},x_{2},0)\}$ 是子空间""超平面上的 $\varphi$ 是线性同构"，课件都是直接断言没给验证）。
  值得跑，但要逐条人工判。

补的时候有三条纪律，细节和实测踩过的坑都在 **`references/proof-gaps.md`**，动手前先读：

1. **"同理"往往并不真的同理** —— 方向可能要对调（实测：Dedekind 定理的两个情形，
   一个用"$A'$ 向下封闭 + $B$ 向上封闭"，另一个必须换成"$B'$ 向上封闭 + $A$ 向下封闭"）。
   不要镜像照抄，重新推一遍。
2. **顺手核对原式本身** —— 实测发现原文把 $\leq$ 写成了 $<$。发现笔误就改，
   并在文中加「订正说明」，否则读者会以为你抄错了。
3. **判断不出原话的，留着别编**，交付时明确列出来。

**手上若有教材 PDF**（课件里"P25""P37"这些页码指的是教材）：补之前先翻对应页，
**优先用教材原有的证法**，别自己另写一套。

### 交付两个版本（**默认都出**）

用户要的是"原文长什么样"和"补全后长什么样"的对照，所以**两份都要给**：

- **原文版** —— 只含课件本身的内容，你补的一个字都不许进去
- **补充证明版** —— 原文 + 你的补充

**写法：只写一份，把补充内容用标记框起来**，再让脚本拆成两份。这样两个版本永远不会走样
（改了共享的错别字，两边同时生效；原文版也**可证明**不含你的东西）。

```markdown
<!--SUPP-->
...新补的证明、解释、注记...
<!--/SUPP-->
```

```
python "<技能目录>\scripts\split_supp.py" notes.md --original orig.md --supplemented supp.md
```

拆之前**先数一遍标记**。`split_supp.py` 只在开闭数量不等时给 `WARNING`，
而它配对的规则是"开标记贪心匹配最近的一个闭标记"——**一旦有块的开标记被误写成闭标记
（或反之），配对就会整片错位，orig.md 会静默地删错内容**，看着还挺正常。
实测踩过：一份 60 页的稿子里 19 个块，其中 16 个 `<!--/SUPP-->` 被写成了 `<!--SUPP-->`
（38 个标记本应严格交替），脚本报"35 open / 3 close"才发现。

自查办法很简单：**标记必须严格交替**——第 1、3、5…个是开标记，第 2、4、6…个是闭标记。
按这个规律重新归一化一遍即可（每个块都是 `开标记 / 内容 / 闭标记`，块与块之间不可能有
两个标记相邻）。

拆完**务必回读一遍 orig.md**，确认没有补充漏进去。两条都要做：

1. 扫残留标记：orig.md 里 `<!--` 出现次数必须是 **0**。
2. 扫补充用语：拿几个**只可能出自我笔下**的短句去 grep（比如"验证如下""下面给出证明"
   "这条注的验证只需一行"）。挑句子时当心假阳性——像"无零因子""消去律"这类词
   **课件原文就有**，会误报；要挑那些绝不可能出现在课件里的表述。

**标记之外还有一处要交代**：正文里若出现「订正」（原文笔误的更正说明），
它**两版都保留**——否则读者对照课件时会以为你抄错了。交付时说明这一点。

### 融入正文，不要写"补充：xxx"（**这条最影响阅读体验**）

标记是给脚本看的，**不是给读者看的**。很多人在补充块里写"**补充：**由于……"，
这是把工作痕迹留在了成品上——读者每遇到一次就被打断一次，像在看一份带批注的草稿。

**要写得像它本来就长这样**：

| 别这么写 | 这么写 |
|---|---|
| **补充：为什么"去心"很重要。** 去心邻域把 $a$ 挖掉了…… | "去心"两个字之所以重要，是因为它把 $a$ 本身挖掉了…… |
| **补充：这两个 $N$ 取多少。** | 要求 $|1/n| < \varepsilon$，即 $n > 1/\varepsilon$。$\varepsilon = 0.1$ 时取 $N = 10$…… |
| **批注这三条课件都没给证明，这里补全。** | 直接接"**证明**：反证法。假设……" |
| **补充：$\lim q^n = 0$ 的证明** | **进一步可以证明 $\lim q^n = 0$（$\|q\|<1$）。** 设 $\|q\|<1$…… |

具体做法：

- **证明接着原文的"证："往下写**，不要另起一个带抬头的段。
- **"课件没有给证明""这里补上"这类话全部删掉**——整理稿里不应该出现整理过程的自述。
- 需要说明某条结论的来历时，**用数学语言说**（"由前面例⑦""由保号性推论二"），
  而不是说"课件在某页提过"。
- 确实要标出处的（跨节引用、教材页码），写成不打断句子的括注。

**唯一例外**是「订正」说明——原文有笔误时必须让读者知道改过。但也别写成抬头，
写成一句括注即可：'（课件上写作 $[a, a-\delta)$，与左邻域对照可知是笔误。）'

### 遇到"另页例"，要指明是第几页

课件里常有"由（另页）例可知""见前面某个例子"这类引用，而**读者手上没有"另页"**。
处理办法：

1. **整理阶段就记页码** —— 逐页读图时顺手记下"第 N 页讲的是哪个例子/定理"，
   形成一张页号索引。有了它，后面才能把引用落到具体页上。
2. **能定位的，在补全时直接写出**："课件第 24 页的例 3 给出的正是这条引理……"
3. **定位不到的，说清楚定位不到**——不要含糊过去，也不要瞎指一页。

若引用指向的是**教材**（"P25 例 2.1.3"），而教材 PDF 也在手边，直接翻那一页核对。

## 第四步：转 docx

```
uv run --no-project --python 3.12 --with pypandoc-binary python "<技能目录>\scripts\md_to_docx.py" notes.md plain.docx
```

**为什么用 pandoc 不用 python-docx**：python-docx 依赖 `lxml`，而 lxml 的原生 DLL
在部分 Windows 机器上被应用程序控制策略拦截（`DLL load failed while importing etree`），
根本 import 不了。pandoc 自带二进制，能把 `$...$` 转成**真正的 Word 公式对象**（可双击编辑）。

转完**看公式数**：`oMath` 为 0 说明 `$` 没被识别，公式全变成了纯文本。

**pandoc 不认的 LaTeX（实测踩过）**：

- **`\tag{}`** —— 那是 LaTeX 的编号宏，pandoc 的数学读取器不支持，用了它整条公式会**退化成纯文本**
  （还会在输出里留一条 `unexpected control sequence \tag` 警告）。课件上的公式编号改成
  `\qquad(1)` 写在公式内部即可。
- **`\vline`（增广矩阵的竖分隔线）** —— 在 `bmatrix`/`pmatrix` 里写
  `\begin{bmatrix} a & b & \vline & c \end{bmatrix` 会整条**退化**（报
  `unexpected "\\"`）。改用 `array` 的列说明符写竖线即可，pandoc 是支持的：
  `\left[\begin{array}{ccc|c} a & b & c \end{array}\right]`。
  **别用 `\begin{array}{c|c}` 之外的花样**，`:`／`!` 这些列修饰符没实测过。
- **`\textcircled{1}` 等圈号字符** —— 不支持（`unexpected control sequence`）。
  课件常用圈号标主元/编号，改成 `\mathbf{1}` 加的文字说明。
- **引号贴着数学定界符** —— `$"$文字$"\Leftrightarrow$` 这种写法会被解析成两段
  内容为引号的"公式"，连带报两条 `unexpected '"'`。引号要放在数学外面：
  `"文字"$\Leftrightarrow$`。
- 转换时**留意 pandoc 的 WARNING**：它是"这条公式没转成原生对象"的唯一信号，
  公式数看着正常但个别式子变成文本，光数数量是发现不了的。

**其他实践要点**：

- 行内 `$...$`、独占一行 `$$...$$`。
- 用例子里出现过的记号，别引入新记号。
- 表格用 pipe 表格（`| a | b |`），pandoc 会转成 Word 表格。

## 第五步：深色 / 浅色

```
python "<技能目录>\scripts\dark_theme.py" plain.docx "笔记_深色.docx" --theme dark
python "<技能目录>\scripts\dark_theme.py" plain.docx "笔记_浅色.docx" --theme light
```

**两版都要给。** 深色版的已知局限：Word 默认不打印页面背景色；部分手机阅读器不显示
段落底纹，会出现**白底白字**。所以浅色版不是备选，是必需品。

技术细节（三块机制为什么缺一不可、OOXML 元素顺序为什么不能乱）见
**`references/ooxml-dark.md`**。

## 第六步：自检（交付前必做）

```
python "<技能目录>\scripts\check_docx.py" "笔记_深色.docx"
```

手工拼的 XML 容易出细微错误，**打不开的 docx 比没有文件更糟**。查七项：
XML 合法性、`w:background` 位置、显示开关、`w:shd` 顺序、**底纹段数与段落数相等**、
公式对象数、残留深色颜色。

**结构检查过了不等于 Word 打得开**，再用 Word 只读打开验一次页数。
**注意两个坑**（详见 `ooxml-dark.md`）：**绝不要调 `$word.Quit()`**（可能附着在用户
正在用的 Word 上，一关就把人家文档关了）；**也不要为了导出 PDF 做视觉确认**——
实测连续挂死并卡住 Cherry 界面，不值得。

## 第七步：交付

- 放到用户能找到的地方（**源 PDF 所在目录**），同时复制一份进会话工作区。
- **不要用 `mcp__cherry-tools__notify` 把 docx 发到微信/手机。** 深色 docx 在手机上打开是
  **乱码**（用户 2026-10-06 实测并明确叫停）。直接交付本地路径就行——把文件放进源 PDF
  同目录，然后在回复里列清楚文件名，用户自己在电脑上打开。
  （只有纯文本通知才适合走 IM；带文件的投递在这条链路上既不可读也不稳定，
  实测连续投递时第 2 条起就报 `prepare failed`，连纯文本都发不出去。）
- **重做一版时，用户很可能正开着上一版在看**，文件被 Word 锁住 → 覆盖时报
  `PermissionError: [Errno 13] Permission denied`。**不要硬覆盖用户正在看的东西**：
  输出到新文件名（加 `_v2` 之类），并在消息里说明"旧文件你还开着，所以换了文件名；
  要换回原名就说一声"。盲目重试覆盖只会反复失败。
- 默认交付**原文版 + 补充证明版**两个 docx（都深色）。若还出了浅色版，一并送上并说明用途。
- 交付说明里必须讲清楚：
  - 补了哪几处、分别补了什么（列清单，让用户能复核）
  - **哪些判断不出、原样留着**
  - 发现并订正的原稿笔误（并说明这条说明两版都留）
  - 原文版是**可证明干净**的（补充标记已全部剥离，回读确认过）
  - 深色版的局限，以及**建议打开看一眼**（深色效果没法自动验证）

## 第八步：把这次的教训写回本技能（**每次都要做**）

**这个技能是靠一次次实测长出来的，不是一次写完的。** 每交付完一批，花几分钟回写一遍。
不回写，下次同样的坑照踩——本文件里现在所有的"实测"字样，都是这么攒下来的。

### 先过一遍这几问

| 这一问 | 命中后写到哪里 |
|---|---|
| 有脚本报错？或者**没报错、但根本没跑**（解释器不对、路径不对）？ | 那个脚本所在的步骤 |
| pandoc 报了 `WARNING`？哪条 LaTeX 没转成原生公式？ | 第四步「pandoc 不认的 LaTeX」清单 |
| 用户提了新要求，或**明确叫停了某个做法**？ | 对应步骤。叫停的要写成"**不要……**"，语气明确 |

| 用户的做法和我原先设想的不一样？ | 对应步骤，**以用户的做法为准** |

### 写到哪（这条最容易做错）

- **每次都要遵守的操作规则 / 判据** → 直接写进 SKILL.md **对应的那一步里**，就近放。
  别一律堆到文末——堆到文末的规则，下次跑的时候没人会翻到。
- **细节、长例子、一次性的排查过程** → 写进 `references/*.md`，SKILL.md 里只留一句指路。
- **环境事实**（解释器在哪、网络限制、Word 的怪癖这类**换台机器就变**的东西）→
  写进跨会话的 FACT.md / 项目记忆，**不要**污染 skill。
- **和这条流水线无关的约定** → 也不要写进来。skill 是要能带到别的机器上用的。

### 三条纪律

1. **SKILL.md 是操作手册，不是日志。** 写"遇到 X 就做 Y"，不写"某年某月某日我遇到 X"。
   日期只在判断新旧确实需要时保留。
2. **同一件事别记两遍**；发现重复就合并。更要紧的是：**发现旧条目和这次实测不符，
   直接改掉**——skill 里的经验也会过期，过期的经验比没有更坏。
3. **写完把 frontmatter 的 `version` 递增一位**（有实质修改就 +0.1）。这样一眼看得出
   交到用户手上的是哪一版经验。

## 脚本

- `scripts/probe_pdf.py` —— 探 PDF 文字层质量，决定走文字提取还是渲染成图。依赖 `pymupdf`。
- `scripts/find_gaps.py` —— 扫出"略去证明"的可疑处 + 完整性检查。纯标准库。
- `scripts/md_to_docx.py` —— md → docx，**公式转成 Word 原生对象**。依赖 `pypandoc-binary`。
- `scripts/split_supp.py` —— 按 `<!--SUPP-->` 标记拆出**原文版 / 补充版**两个文件。纯标准库。
- `scripts/dark_theme.py` —— 深色/浅色换肤 + 补 CJK 字体。**纯标准库。**
- `scripts/check_docx.py` —— 结构自检。**纯标准库。**

**怎么调解释器（实测）**：本机 PATH 上的 `python` 是 Microsoft Store 的占位 stub，
直接调会报"Python was not found"。三种都可用的写法：

1. `uv run --no-project --python 3.12 python "<脚本>" ...` —— 通用，但每次要解析一遍。
2. 直接用 uv 管理的解释器（最快，纯标准库脚本首选）：
   `C:\Users\tryqt\AppData\Roaming\uv\python\cpython-3.12-windows-x86_64-none\python.exe`
3. `md_to_docx.py` 必须走 `uv run --with pypandoc-binary ...`（pandoc 二进制由它带进来）。

装包走清华镜像：`$env:UV_DEFAULT_INDEX = "https://pypi.tuna.tsinghua.edu.cn/simple"`。
